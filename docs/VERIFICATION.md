# Verification Process

**⚠️ IMPORTANT: NOT INSURANCE.** Preview Bond is a structural verification tool providing proofs of transaction integrity. It is NOT a financial insurance product and does not provide guaranteed monetary reimbursement for all types of losses.

The goal of verification is to deterministically prove whether a transaction's actual execution matched its simulated preview.

## 1. The Verification Loop

Verification is a comparison between two states:
- **Expected State**: Generated by the Simulator during the `DECLARE` phase.
- **Actual State**: Extracted from the Solana ledger after the transaction lands.

### Step-by-Step Logic
1. **Detection**: The Keeper identifies the `tx_digest` on-chain.
2. **Extraction**: The Keeper calls `getTransaction` with `innerInstructions` enabled.
3. **Reconstruction**: The Keeper rebuilds the structural fingerprint from the actual logs and instructions.
4. **Comparison**:
   - If `ActualFingerprint == ExpectedFingerprint` $\rightarrow$ `MATCH`.
   - If `ActualFingerprint != ExpectedFingerprint` $\rightarrow$ `MISMATCH`.

## 2. Deep Dive: The 4 Covered Checks

### Check 1: Hidden Token Transfer
- **Logic**: The Keeper iterates through all `transfer` and `transferChecked` instructions. If any transfer moves tokens from a user-controlled account to an address not listed in the Expected State, it is a violation.
- **Evidence**: `Instruction: TokenProgram::Transfer { from: User, to: Unknown, amount: X }`.

### Check 2: Surprise Program (CPI)
- **Logic**: The Keeper examines the list of all programs invoked during the transaction. Any Program ID not present in the Expected State's program list is a violation.
- **Evidence**: `CPI: ProgramID(Unexpected) called`.

### Check 3: Authority Change
- **Logic**: The Keeper compares the account state before and after the transaction for all accounts involved. Any change in the `owner` or `authority` field of a user-controlled account is a violation.
- **Evidence**: `Account(UserAccount).authority: OldAddr -> NewAddr`.

### Check 4: Wrong Program Execution
- **Logic**: The Keeper checks the primary program ID of the transaction. If it differs from the one declared in the `DECLARE` phase, it is a violation.
- **Evidence**: `Expected: ProgA, Actual: ProgB`.

## 3. Edge Cases & False Positives

### Token-2022 Support
- **Current Status**: Unsupported by default in v1.
- **Behavior**: Transactions using Token-2022 extensions that modify structural state may be rejected or marked as `NOT_COVERED` to avoid false positives.

### Harmless Mismatches
A mismatch does **not** automatically trigger a status change to `ClaimPaid`. 
- **Example**: A program makes an unexpected CPI to a logging program that doesn't move funds or change authority.
- **Result**: `MISMATCH` detected $\rightarrow$ `Realized Loss = 0` $\rightarrow$ **No status change to ClaimPaid**.

## 4. Evidence Sources
The Keeper uses the following Solana RPC methods for evidence:
- `getTransaction`: For instructions, logs, and inner instructions.
- `getAccountInfo`: For verifying authority changes.
- `getMultipleAccounts`: For pre/post balance checks.
